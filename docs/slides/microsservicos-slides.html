Monólito e microsserviços

Monólito

Um sistema, comunicação dentro do código, deploy único e operação mais simples no início.

Microsserviços

Vários serviços, comunicação pela rede, deploy por serviço e operação distribuída.

Começar com um monólito é uma escolha válida. A divisão passa a fazer sentido quando escala, equipes e ciclos de mudança justificam o custo adicional.

O que é um microsserviço?

Capacidade de negócio

Resolve uma parte clara do domínio.

Execução independente

Possui processo e ciclo de vida próprios.

Contrato explícito

Conversa com outros serviços por API ou evento.

Analogia da praça de alimentaçãoCada restaurante prepara seu próprio tipo de comida, tem equipe e cozinha próprias, mas todos seguem regras comuns para atender clientes dentro do mesmo espaço.

REST, GraphQL e gRPC

REST

Usa HTTP, recursos, métodos e status codes. É comum em aplicações web e mobile.

GraphQL

Permite que o cliente escolha exatamente os dados que deseja receber.

gRPC

É eficiente para comunicação interna de alta performance entre serviços.

Nenhum estilo resolve todos os cenários. A escolha depende do consumidor, do contrato e das necessidades de desempenho.

Endpoints e métodos HTTP

GET    /api/v1/users       lista usuários
POST   /api/v1/users       cria um usuário
GET    /api/v1/users/123   busca pelo identificador
PUT    /api/v1/users/123   atualiza o recurso
DELETE /api/v1/users/123   remove o recurso

O endpoint representa um recurso. O método HTTP informa a ação que será realizada sobre esse recurso.

Por que adotar microsserviços?

Escala

Aumenta apenas os serviços mais exigidos.

Deploy

Publica mudanças sem implantar o sistema inteiro.

Equipes

Permite desenvolvimento paralelo com maior autonomia.

Tecnologia

Cada serviço pode usar ferramentas adequadas ao seu problema.

A autonomia só existe de verdade quando serviço, dados, contrato e ciclo de entrega possuem limites claros.

Rede, falhas e consistência

Rede

Chamadas podem sofrer latência, timeout ou indisponibilidade.

Resiliência

Timeout, retry e circuit breaker ajudam a conter falhas.

Dados

Serviços podem enxergar estados diferentes por algum tempo.

HTTP é síncrono: quem chama espera. Eventos são assíncronos: o produtor publica e continua, reduzindo a dependência temporal.

Quando usar ou evitar microsserviços?

Considere

Sistema grande, equipes diferentes, cargas distintas e necessidade real de deploy independente.

Evite por enquanto

Projeto pequeno, equipe reduzida, domínio instável ou pouca capacidade de operação.

Na migração, o Strangler Fig Pattern extrai funcionalidades gradualmente. API First define contratos antes de mover implementação e dados.

Resumo

Divisão

Microsserviços representam capacidades de negócio.

Conexão

APIs definem contratos entre clientes e serviços.

Qualidade

Segurança, documentação e monitoramento são obrigatórios.

Trade-off

Autonomia aumenta, mas rede, dados e operação ficam mais difíceis.

Microsserviços dividem responsabilidades. APIs conectam essas responsabilidades de forma padronizada. Use essa combinação quando o problema justificar sua complexidade.
