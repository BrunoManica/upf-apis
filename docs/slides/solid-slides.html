S: uma razão para mudar

Controller

Recebe HTTP, valida a entrada e delega.

Service

Orquestra a regra do caso de uso.

Repository

Conversa com o MongoDB.

Analogia da cozinhaO garçom recebe o pedido, o cozinheiro prepara e o caixa cobra. Se uma pessoa fizer tudo, qualquer mudança vira confusão. Na API, controller, service e repository também precisam de papéis claros.
Responsabilidade única não significa “uma classe com um método”. Significa agrupar aquilo que muda pelo mesmo motivo.

S / separação práticaresponsibilities split

O service passa a orquestrar

public Payment createPayment(CreatePaymentRequest request) {
    PaymentProcessor processor =
        processorResolver.resolve(request.type());

    ProcessedPayment processed = processor.process(request);
    Payment payment = PaymentMapper.mapFrom(request, processed);

    return paymentRepository.save(payment);
}

O `PaymentService` não precisa saber gerar QR Code, mascarar cartão ou montar boleto. Ele coordena quem sabe fazer cada parte.

O / open closedextend without editing

O: extensão sem cirurgia

Fechado para extensão

Cada novo pagamento adiciona outro `else if` no mesmo service.

Aberto para extensão

Um novo tipo entra como uma nova classe que cumpre o contrato.

Analogia da tomadaPara ligar um aparelho novo, você não quebra a parede e refaz a instalação elétrica. O aparelho apenas respeita o padrão da tomada. Uma nova estratégia de pagamento deve respeitar o contrato sem exigir reforma no service.

Adicionar comportamento deve exigir mais código novo e menos alteração em código estável.

L: trocar sem surpresa

Se o código espera um `PaymentProcessor`, qualquer implementação válida precisa funcionar naquele lugar.

PIX

Recebe request e devolve resultado processado.

Cartão

Respeita o mesmo contrato e não muda a expectativa.

Pode substituir as outras estratégias no fluxo.

Analogia da lâmpadaSe duas lâmpadas usam o mesmo encaixe, você espera trocar uma pela outra e continuar tendo luz. Se uma delas desliga a casa inteira, ela cabe fisicamente, mas quebra o comportamento esperado.

12 / 20
L / contrato honestono hidden exception

Não prometa o que não suporta

Problema

Uma implementação lança `UnsupportedOperationException` para um método obrigatório da interface.

Melhoria

O contrato contém somente operações que todas as implementações conseguem cumprir.

Liskov não é apenas “usar herança”. É preservar o comportamento esperado por quem depende do contrato.

Separe por capacidade

PaymentProcessor

Processa um tipo de pagamento.

Notifica o cliente quando necessário.

ReportExporter

Exporta relatórios quando necessário.

Analogia do controle remotoUm controle de ventilador precisa ligar, desligar e ajustar velocidade. Obrigar esse controle a ter botões de Netflix, volume e troca de canal cria funções que ele nunca poderá cumprir.
Uma classe implementa apenas o contrato que realmente usa. Isso reduz métodos vazios, exceções artificiais e dependências desnecessárias.

D / dependency inversiondetails isolated

D: dependa do contrato

public PaymentService() {
    this.repository =
        new MongoPaymentRepository();
}
public PaymentService(
    PaymentRepository repository
) {
    this.repository = repository;
}
Analogia do carregadorO celular depende de uma entrada USB-C, não da fábrica específica do carregador. Você pode trocar o carregador desde que ele respeite o padrão. O service depende de `PaymentRepository`, não de uma construção concreta feita com `new`.

Criar a dependência com `new` prende a regra ao detalhe concreto. Receber a dependência pelo construtor deixa o Spring montar o objeto.

resultado / antes e depoisrefactor complete

O que mudou de verdade?

Antes

Uma classe grande, `if` por tipo, detalhes concretos e testes difíceis.

Depois

Service orquestrador, estratégias focadas, contratos pequenos e dependências injetadas.

A melhoria não está em ter mais arquivos. Está em conseguir mudar uma parte sem precisar entender e arriscar todas as outras.

review / erros comunsquality gate

Erros comuns

  • Criar interface sem existir uma necessidade real de variação.
  • Transformar cada método em uma classe e fragmentar demais o código.
  • Achar que SOLID significa usar herança em todo lugar.
  • Criar uma interface gigante com todas as operações do sistema.
  • Colocar regra de negócio no controller, DTO ou model do MongoDB.
